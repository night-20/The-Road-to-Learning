**目标**：掌握缓存穿透 / 击穿 / 雪崩解决方案

### 学习内容

- **下午 3h** — 实现三个核心场景：
  - ① Cache Aside 缓存商品详情
  - ② Redisson 分布式锁防超卖
  - ③ 布隆过滤器防缓存穿透
- **晚上 2h** — 接入项目：给 Day 1 的用户查询加 Redis 缓存，设置过期策略

### 三大缓存问题对比

|问题  |原因             |解决方案               |
|----|---------------|-------------------|
|缓存穿透|查询不存在的数据       |布隆过滤器 / 缓存空值       |
|缓存击穿|热点 Key 过期瞬间大量请求|Redisson 互斥锁 / 逻辑过期|
|缓存雪崩|大量 Key 同时过期    |过期时间随机抖动 + 多级缓存    |

## 面试必备：3 个高频问题

### Q1：Redis 缓存击穿你怎么处理？

> 缓存击穿是热点 Key 过期的瞬间大量请求打到数据库。我用了两种方案：
> 一是 **Redisson 互斥锁**，只让一个线程去重建缓存，其他线程等待；
> 二是**逻辑过期**，Key 永不真正过期，在 value 里存一个过期时间，发现过期后异步重建，其他请求先返回旧数据。
> 前者一致性好但有等待，后者性能高但短暂数据不一致，我根据业务场景选择。

### Q2：分布式锁的实现原理？

> 我用 Redisson 的 `RLock`，底层是 `SET key value NX PX timeout` 原子命令加锁，通过 Lua 脚本保证释放锁的原子性（判断 value 是否是自己的再删除）。
> Redisson 还内置了**看门狗机制**，每隔 1/3 超时时间自动续期，防止业务没执行完锁就过期的问题。

### Q3：为什么用 MQ 而不是同步调用？

> 同步调用的问题是：下单接口需要等库存服务响应，如果库存服务慢或宕机，下单直接失败，用户体验差。
> 用 MQ 后，下单写完订单记录就可以立即返回，库存扣减异步进行，接口响应时间从 200ms 降到 50ms。
> 同时 MQ 天然做了流量削峰，秒杀场景下大量订单消息积压在队列里，库存服务按自己的节奏消费，不会被打垮。
