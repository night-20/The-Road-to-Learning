前端发 GET /api/user/1 请求，后台执行了哪几步？

用户查询走的是 Cache-Aside 模式。请求进来先查 Redis，缓存命中直接返回，耗时 1ms 左右；缓存未命中则回源查 MySQL，查到后回写 Redis 并设置过期时间，再返回给前端

如果有人同时查 zhangsan 问了 100 次，你们的系统怎么保证只查一次数据库？

"假设有 100 个请求同时查一个热点用户，缓存刚好过期了。
如果这 100 个请求全部打到数据库，数据库就崩了——这叫 缓存击穿。
我们的做法是：用 Redis 的 SETNX 命令做一个分布式锁。相当于 100 个人里面只选一个代表去查数据库，查到后把结果写回 Redis 缓存。剩下 99 个人发现缓存更新好了，直接从缓存读，不用再查库。
简单说就是：互斥锁保证同一时刻只有一个线程重建缓存，其他线程等待或降级兜底。"

你们项目为什么用统一返回结果 Result，而不是每个接口自己拼 JSON？

主要为了统一规范。多人协作时，不同接口返回格式一样，前端和后端之间、后端开发之间，看一眼 code 就知道请求成没成功，不用猜。而且报错时排查也快，因为所有错误都是同一个结构。
